# Apparel Group – Audit Management System (Backend)

REST API powering the Apparel Group Audit Management System — audit creation and review workflow, cash reconciliation, notifications, PDF report generation, and email alerts.

## Tech Stack

- **Runtime:** Node.js + Express 5
- **Database:** PostgreSQL (`pg`)
- **Auth:** JWT (`jsonwebtoken`) + `bcrypt` for password hashing
- **PDF:** `pdfkit` — generates the audit findings + cash reconciliation report
- **Email:** `nodemailer`
- **Utilities:** `cors`, `dotenv`, `chalk` (request logging)
- **Dev:** `nodemon` (not wired into a script by default — see [Running the server](#running-the-server))

## Prerequisites

- Node.js 18 or later
- PostgreSQL 14 or later
- npm

## Setup

1. Install dependencies:
```bash
   npm install
```

2. Create a PostgreSQL database:
```sql
   CREATE DATABASE audit_db;
```

3. Create a `.env` file in the backend root:
```env
   DB_HOST=localhost
   DB_PORT=5432
   DB_USER=postgres
   DB_PASSWORD=your_password
   DB_NAME=audit_db

   JWT_SECRET=replace_with_a_long_random_string
   PORT=5000

   # Used to build clickable links inside notification/status emails
   APP_BASE_URL=http://localhost:5173
   APP_LOGIN_URL=http://localhost:5173/login

   # SMTP credentials read by config/mailer.js
   SMTP_HOST=smtp.example.com
   SMTP_PORT=587
   SMTP_USER=your_smtp_user
   SMTP_PASS=your_smtp_password
```

4. Create the database schema:
```bash
   node DataBase/initDB.js
```
   Creates every table (`Brands`, `Locations`, `OpsManagers`, `StoreManagers`, `Stores`, `MajorCriteria`, `AuditPoints`, `Roles`, `Users`, `AuditAssignments`, `AuditEvaluations`, `Notifications`) and safely re-applies `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` on every run — safe to re-run any time.

5. Seed the system roles and the first administrator. There is no automated seed script for these — `POST /api/users/createUser` explicitly refuses to create a `RoleID = 1` account — so insert them directly:
```sql
   INSERT INTO Roles (RoleID, RoleName) VALUES
     (1, 'Admin'),
     (2, 'Ops Manager'),
     (3, 'Store Manager'),
     (4, 'Auditor'),
     (5, 'Audit Manager');
```
   Generate a bcrypt hash for the admin password:
```bash
   node -e "console.log(require('bcrypt').hashSync('admin123', 10))"
```
   Then insert the admin user with that hash:
```sql
   INSERT INTO Users (OracleID, UserName, Password, LocationID, RoleID)
   VALUES (1, 'Admin', '<bcrypt-hash-here>', NULL, 1);
```
   **Change this password immediately after the first login.**

   *(Optional)* `DataBase/insertDB.js` contains commented-out sample Brands / Locations / MajorCriteria / AuditPoints inserts — uncomment and run with `node DataBase/insertDB.js` to seed reference data for testing.

## Running the Server

`package.json` currently only defines a placeholder `test` script — there is no `start` or `dev` script wired up. Run the server directly:

```bash
node server.js
```

For auto-restart on file changes during development (uses the `nodemon` devDependency already installed):

```bash
npx nodemon server.js
```

The API will be available at `http://localhost:5000/api`.

> Tip: add `"dev": "nodemon server.js"` and `"start": "node server.js"` to the `scripts` section of `package.json` if you'd like to run these as `npm run dev` / `npm start`.

## Authentication

Two login endpoints:

- **`POST /api/users/login`** — `{ OracleID, Password }`. Personal account login for Admin, Ops Manager, Store Manager, Auditor, and Audit Manager.
- **`POST /api/users/store-login`** — `{ StoreCode, Password }`. Store account login (Store Manager–level access scoped to one store), using the password set via `PATCH /api/users/stores/:storeSerial/set-login`.

Both return a JWT (8h expiry, signed with `JWT_SECRET`) carrying role and identity claims, verified on protected routes by `middleware/verify-token.js`. Admin-only routes are additionally guarded by `middleware/isAdmin.js`.

## User Roles

| Role | ID | Access |
|---|---|---|
| Admin | 1 | Full system access |
| Ops Manager | 2 | Reviews audits forwarded from the Audit Manager, routes to Store Manager |
| Store Manager | 3 | Adds the action plan and target date for audits sent to their store |
| Auditor | 4 | Conducts audits, submits and revises findings |
| Audit Manager | 5 | First-line review of submitted audits — approve & forward, request revision, or reject |

## Audit Workflow



Every status transition:
1. Creates an in-app notification (`Notifications` table) for the user/role responsible for the next step.
2. Sends an email (via `services/emailTemplates.js` + `config/mailer.js`) with a PDF snapshot of the audit attached (generated by `services/auditPdf.js`), when a valid email address is on file. Email failures are caught and logged — they never block the API response.

## Data Handling Policy

Deletion is **permanent**. Dependent records either cascade at the database level or are blocked with a `409` if references still exist (see the `DELETE` routes under `controllers/admin/*` and `controllers/Employee/Auditor.js`). Deleting a user detaches (not deletes) their historical `AuditAssignments` so audit history is preserved, while their notifications are removed.

Treat every delete as final and irreversible. Keep regular database backups.

## Deployment Notes

- Set `JWT_SECRET` to a strong, unique value — never reuse the development value.
- Point `APP_BASE_URL` and `APP_LOGIN_URL` at the production frontend domain.
- Use production SMTP credentials; without them, `sendMail` fails silently and no emails go out, but the app keeps working.
- Ensure `cors` origins are restricted appropriately in production if you lock down `server.js`'s CORS config.
